## Findings Summary

### Solid Foundations ✓

1. **Three-layer mutation discipline**
   - Effects orchestrate → Handlers invoke mutators → Mutators produce state
   - Clear separation of concerns, testable boundaries
   - Payload + Mutator registry pattern enables atomic multi-target changes

2. **State-based evaluator (ICommandPipeline + GameRules)**
   - Deterministic evaluation via pure functions over immutable state slices
   - Snapshot/rollback capability baked in from design
   - Service injection allows game-specific extensibility

3. **Trigger fold + subscription model (ADR-0005)**
   - Entity-owned triggers via InstanceId as stable subscription key
   - Survives CardRef rotation and snapshot/restore cycles
   - Boundary-correct subscription lifecycle

4. **CardRef rotation mechanism**
   - Clever privacy/visibility projection
   - Decouples internal (InstanceId) from external (CardRef) identity
   - Enables zone visibility semantics cleanly

5. **Scaffold state bridge**
   - Store-canonical, Entities-as-API pattern solid
   - StateEntity<TDef> handle provides unified access
   - Subscriptions coalesce notifications efficiently

## Pain Point 1: Entity State Usage

### Current Architecture

- **Store is canonical.** Game state lives in immutable slices (Store<GameState>).
- **Entities API bridges to Store.** StateEntity<TDef> wraps slices, provides read/mutation surfaces.
- **Each entity = one slice.** LinearCard gets CardSlice, etc. Scales O(entities).
- **InstanceId = stable identity.** Entities register triggers via InstanceId; survives snapshots.
- **CardRef = temporary projection.** Rotates on move/visibility; external-facing token.

### Identified Fragilities

1. **One slice per entity scales linearly**
   - Store<GameState> grows a field per entity type
   - GameState becomes "union of all possible entity types"
   - Snapshot includes all slices, even if game uses subset

2. **Handle re-creation across snapshots**
   - StateEntity<TDef> is created fresh from slice on every access
   - No pooling; allocation pressure on hot paths (triggers, effect evaluation)

3. **Dual registration channels**
   - CardMapState + IEntityRegistry both track entities
   - Discipline constraint: both must stay in sync
   - No compile-time guarantee; runtime fragility

4. **Discipline-only constraints throughout**
   - Payload handler must dispatch matching payload type
   - Entity definition must register all triggers used by effects
   - No type safety; enforcement via code review

5. **Multi-store deferral**
   - Currently single Store<GameState>
   - Future game systems (asset store, tutorial state) deferred
   - Unclear how to coordinate snapshots across multiple stores

### Recommendation

- Establish strict handle lifecycle: create-once-at-snapshot, reuse within evaluation cycle
- Consider handle pooling for high-frequency access (triggers, effects)
- Formalize entity registry invariants (consider sealed registry at setup time)

## Pain Point 2: Cards and Their Variables

### Current Architecture

- **Cards are StateEntity<CardDefinition>**
- **Variables stored as key-value:** `GetVariable<T>(key)` where key is string
- **Modifier stacks with source attribution:** ModifierSource(InstanceId) enables cleanup
- **VariableValue as class hierarchy:** Base + Numeric/String subclasses
- **CardRef dual-identity:** InstanceId (stable) + CardRef (rotating)
- **CardMapState holds two parallel dictionaries:** `Cards: <CardRef,Card>` and `RefByCard: <Card,CardRef>`

### Identified Fragilities

1. **VariableValue as reference type**
   - Every modifier, every counter, every stat is a boxed object
   - Class hierarchy (VariableValue base + Numeric/String) forces polymorphism
   - Allocation on every read/write; pressure on GC

2. **String-keyed variables**
   - No type safety; `GetVariable<int>("Durability")` is unverified
   - Fragile to rename/refactor
   - No discovery of "what variables does this card have?"

3. **Two-ID model cognitive cost**
   - InstanceId for internal simulation
   - CardRef for external/transport
   - Confusion points: which ID to use in triggers? In effects? In zone contents?
   - RefByCard parallel dictionary required for rotation

4. **Dual parallel dictionaries in CardMapState**
   - Cards: `<CardRef, Card>` (lookup by reference)
   - RefByCard: `<Card, CardRef>` (reverse lookup)
   - Both must stay in sync; both snapshot; allocation overhead

5. **Missing mutation-surface discipline**
   - Effects can read card properties but mutation surface unclear
   - Payload/Mutator pattern enforces atomic changes but not all properties have mutators
   - Extensibility story for adding new properties unclear

6. **No authoring story**
   - How do game designers define card variables?
   - Where do defaults come from?
   - How to ensure modifiers respect bounds?
   - No documentation of card variable lifecycle

### Recommendation

- **Consider externalizing CardRef** (see architectural insight below)
- Audit VariableValue use; consider struct-based approach for primitives
- Define canonic card variable set and generation story
- Formalize mutation surface: which properties are mutable, via which actions

## Pain Point 3: Performance & Memory Management

### Allocation Tracing: Single MoveCardCommand

Traced allocations through a typical move operation (card from hand to board):

```
MoveCardCommand
  → GameRules.Evaluate
    → DispatchMoveCardAction
      → MoveCardMutation handler
        → CreateCardMutation (for rotation)
          → NewSlice(prev, fields...)  [1 alloc: new CardSlice]
          → ImmutableDictionary.SetItem (2-3 allocs: dict rebalance)
          → StateEntity creation [1 alloc: handle]
          → VariableValue reads [N allocs: per variable access]
          → ModifierStack.ApplyDeltas [M allocs: per modifier]
      → SetCardVisibilityMutation
          → NewSlice [1 alloc: new VisibilitySlice]
          → ImmutableDictionary operations [2-3 allocs]
      → CardMapState update
          → Remove old CardRef entry [2-3 allocs: dict rebalance]
          → Add new CardRef entry [2-3 allocs: dict rebalance]
          → Snapshot of RefByCard [2-3 allocs]
      → Trigger evaluation
          → Handle re-creation per trigger [N allocs: per trigger]
          → Effect dispatch [M allocs: per effect]
          → Payload allocation [1 alloc per effect]
      
Typical estimate: 30-60 allocations per single MoveCard command
Typical turn (Slay-the-Spire scale): 350-500 allocations per turn
```

### Where immutability earns back its cost

1. **Snapshot/rollback** — entire game state captured for undo, replay, AI lookahead
2. **Determinism** — pure evaluation enables replay from action log
3. **Coalesced notifications** — multiple mutations produce one delta; subscribers notified once
4. **Structural sharing** — ImmutableDictionary shares unchanged nodes across snapshots

### Where cost is problematic

1. **Stacklands real-time tick incompatible**
   - Framework designed for turn-based games (action → evaluate → next action)
   - Real-time games need continuous tick loop (30-60 fps)
   - Current design allocates on every action; tick loop would allocate per frame

2. **VariableValue class hierarchy**
   - Every variable access boxes; every read/write creates object
   - No escape analysis; all boxes escape to field stores

3. **Two parallel dictionaries in CardMapState**
   - RefByCard snapshot on every card rotation
   - Lookup inefficiency vs benefit questionable

4. **No object pooling**
   - Handle re-creation, payload allocation all fresh
   - GC pressure linear with action count

5. **ImmutableList history**
   - ActionLog stored as ImmutableList<Action>
   - Snapshot produces O(turns) allocations for history copy

6. **Snapshot allocation**
   - Each snapshot produces new Store<GameState> instance
   - All slice fields deep-copied
   - AI with 10 lookahead turns = 10 snapshots

### Critical gaps

1. **No performance budget**
   - No target for allocations per action, per turn, per frame
   - No perf tests; regressions invisible

2. **No authoring story**
   - How do designers create custom variables?
   - How to extend card properties without mutating core Card type?

3. **Effect recipes**
   - No high-level patterns for common effects (aura, buff, debuff)
   - Designers must write trigger subscriptions manually

4. **HistoryEnvelope typing fragile**
   - Type-only Wait<TCommand> routing in effect handlers
   - No compile-time guarantee that handler handles the command type

5. **Real-time tick undesigned**
   - Turn-based model incompatible with Stacklands tick loop
   - Would require architectural revision (streaming evaluator, pooling, etc.)

### Recommendation

- **Establish perf budget** (e.g., <50 allocations/action, <1ms/action)
- **Spike VariableValue struct approach** for primitives
- **Prototype object pooling** on hot paths (handles, payloads)
- **Design real-time tick** as separate evaluator mode (deferred)
- **Add perf tests** to CI; block regressions

## Architectural Insight: CardRef Externalization

### Current Model

- Card is StateEntity<CardDefinition> with embedded IReference (contains CardRef)
- CardMapState holds `Cards: <CardRef, Card>` + `RefByCard: <Card, CardRef>`
- CardRef rotates on move/visibility change (creates new Card slice)
- InstanceId is stable internal identity; CardRef is external/temporary

### Proposed Model

CardRef is not Card state; it's a **visibility projection**. Move it external:

```
Simulation layer:
  - Card is pure StateEntity (entity state only)
  - Zones reference cards by InstanceId
  - Triggers subscribe to InstanceId
  
Transport/Visibility layer:
  - Immutable map <CardRef, InstanceId> (or <CardRef, Card>)
  - CardRef rotates: remove old entry, add new entry
  - UI/client projects CardRef on demand
```

### Benefits

1. **Eliminates RefByCard dictionary** — one allocation source gone
2. **Simpler snapshots** — do you snapshot CardRef at all, or regenerate from visibility rules?
3. **Cleaner separation** — simulation uses InstanceId; transport uses CardRef
4. **CardRef rotation is map update** — not a Card state mutation
5. **Snapshot memory** — CardRef keys don't bloat snapshot size

### Trade-offs to validate

1. **Who owns CardRef map?** EntityCardSystem? CardMapState refactored?
2. **Snapshot regeneration** — is CardRef deterministic from visibility state? Can it be?
3. **In-flight reference stability** — can CardRef change mid-turn? (Probably gated by visibility timing.)
4. **Zone storage** — do zones store CardRef or InstanceId? (Should be InstanceId.)

### Recommendation

**Spike:** Refactor CardMapState to hold only Cards slice; maintain CardRef map separately. Write visibility rule engine that regenerates CardRef on snapshot restore. Trace MoveCard + visibility change through new model. If logic holds and allocations drop, accept the architectural change.

## Overcomplications & Opportunities

### Overcomplications

1. **Two-ID model**
   - InstanceId + CardRef duality is sophisticated but cognitively taxing
   - Confusion points everywhere (which ID in triggers? zones? effects?)

2. **One slice per entity**
   - GameState grows field per entity type
   - Snapshot includes unused slices
   - Consider sparse entity store instead

3. **OnQueueDrained kitchen sink**
   - Handles subscription cleanup, turn signals, rule evaluation
   - Too many concerns; candidates for extraction

4. **Parallel dictionaries**
   - RefByCard exists only for rotation lookup
   - CardRef externalization eliminates this

### Opportunities

1. **CardRef externalization** (identified above)
2. **Handle pooling** on hot paths (triggers, effects)
3. **VariableValue struct** for primitive values (int, bool, float)
4. **Perf budget + tests** to prevent regression
5. **Effect recipe library** for common patterns (aura, buff, conditional)
6. **Zone model spike** — can zones use InstanceId instead of CardRef?

## Conclusion

Card-Framework has **solid architectural foundations** (three-layer mutation, state-based evaluation, trigger subscriptions, snapshot/rollback). 

**Primary pain points are solvable** via targeted spikes:
- CardRef externalization (architectural improvement)
- VariableValue struct prototype (allocation reduction)
- Perf budget + tests (visibility + prevention)
- Entity registry formalization (fragility reduction)

**Real-time tick is a design gap**, not a bug fix. Separate spike required.

**Next critical decision:** CardRef externalization. If successful, simplifies multiple downstream concerns and recovers meaningful allocations. Recommend immediate spike.
