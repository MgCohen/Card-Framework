## CONCERN 1: Entity State Usage

### What the docs commit to

Store is canonical; Entities is the API.

Every runtime "thing" (card, token, attachment, equipment, player) is a StateEntity<TDef> handle over a per-instance EntityVariableState slice in the Scaffold Store. The slice carries:

- **BaseValues** — override-only ImmutableDictionary<Variable, VariableValue> (falls back to definition.TryGetDefaultValue(var) for unset keys).
- **ModifierStacks** — ImmutableDictionary<Variable, IReadOnlyList<ActiveModifier>>, ordered ascending by Modifier.Order (FIFO ties).
- Plus StoreVariableStorage adapter holding a per-rebuild effective-value cache.

Six bridge payloads cover every variable mutation: AddModifier, RemoveModifier, RemoveModifiersBySource, SetBaseValue, AddEntityVariable, RemoveEntityVariable.

### The tradeoff that's working

1. **Single source of truth.** No duplication, no two-way sync between "entity object" and "store slice." This was a real risk and you killed it cleanly.
2. **Snapshot/rollback for free.** LoadSnapshot rehydrates handles from canonical slices.
3. **Modifier source attribution.** ModifierSource = attachment.InstanceId makes attachment death cleanup a one-liner: RemoveModifiersBySourcePayload(target, new ModifierSource(attachment.Id)). Equipment, auras, status effects all collapse to one mechanism.
4. **Polymorphism via IReadOnlyEntity<TDef> / IMutableEntity<TDef>.** Code can be written against either authoring instances or state-backed entities.

### What is fragile

1. **One slice per entity scales linearly.** A 60-card deck = 60 EntityVariableState slices. Add zones (separate ZoneContentsState), the card map, ownership, visibility, modifier sources, and a turn's worth of history envelopes — you're easily at 200–300 slices in the Store before any game logic runs. Subscriptions, lookups, and snapshot-load all scale with this. There's no published target; we don't know what's "fine" yet.

2. **The handle (StateEntity<TDef>) is a class, not a record**, with an OnEntityRemoved event and per-handle IDisposable. It's deliberately not BaseState. But subscribers that attach via entity.Subscribe(key, …) need to handle re-creation across LoadSnapshot — the old handle is gone, the new handle has no listeners. The doc acknowledges this ("projections that need to bind on rollback must re-subscribe through IEntityRegistry") but it's a footgun the moment you have presentation views bound to entities.

3. **Two registration channels for entity handles.** Cards live in CardMapState (a Store slice that holds Card handles directly). Other entity kinds use the engine's separate IEntityRegistry. Snapshot-load rehydrates them differently. Two recovery paths, not one — and the engine still owns an InstanceId → definition registry "typically a sibling slice that records 'what was spawned' so the restore knows which TDef to instantiate" (entities/02 §5.4). That sibling slice isn't designed yet.

4. **AddEntityVariable discipline is easy to misuse.** It's reserved for variables not declared in the definition. WithVariable is a no-op for declared keys (and AddVariable returns false), so misuse fails silently. An author who calls AddVariable for everything ends up with BaseValues shadowing every definition default and never realizes it.

5. **SetBaseValuePayload is a discipline-only fallback channel.** "Use AddModifier for effect-tracked, use SetBaseValue for out-of-band (level-up, save load, authoring tools)." That distinction lives in prose, not in types. A handler dispatching SetBaseValuePayload from inside an effect is a violation no compiler catches.

6. **Multi-store entities are deferred.** "Currently EntityStateFactory.Create is parameterized on a single Store. Multi-store games (player-private stores, instance-shard stores) would need registry partitioning. Out of scope until a multi-store game arrives." This becomes load-bearing the second you want hidden information enforced server-side rather than filtered at transport.

### Options if you want to move

1. **Accept it as-is.** It's correct, well-bridged, and the team has clearly invested in making the bridge clean. The fragility is mostly ergonomic, not architectural.

2. **Tighten discipline with types.** Move SetBaseValue and AddEntityVariable behind separate interfaces (IAuthoringMutableEntity?) so handlers can't reach them by default. Cheap to do.

3. **Collapse the dual registration.** Pick one: either everything lives in a slice-keyed map (the CardMapState pattern, generalized to all entity kinds), or everything lives in an engine-side IEntityRegistry. The current split exists because cards needed CardRef-keyed lookup that other entities don't — but solving it once is cheaper than maintaining two paths.

## CONCERN 2: Cards and Their Variables

### What the docs commit to

- One Card : StateEntity<CardDefinition>, IReference class. Variants (Fireball, Goblin) are different CardDefinition instances, not subclasses.
- Two IDs per card:
  - **InstanceId** (typed Identifier<Instance>) — stable, used for variable storage, modifiers, ownership, history, server-internal subscriptions.
  - **CardRef** (record struct(Guid)) — temporary; the CardMapState key, the entry in ZoneContentsState, transport-visible. Rotates on every move and every visibility transition.
- Variable is (string Key, string PayloadTypeId). VariableValue is an abstract class with concrete subclasses tagged [VariableValueId("int")] etc. Built-in modifiers ship as IntAddModifier, IntMultiplyModifier, FloatAddModifier, etc.
- CardMapState holds two parallel ImmutableDictionarys — Cards : ImmutableDictionary<CardRef, Card> and RefByCard : ImmutableDictionary<Card, CardRef> — to make RefOf(card) O(1).
- ModifierFactory allocates deterministic IDs from an engine counter (snapshotted), preventing Guid.NewGuid() from leaking into modifier ids.

### What's solid here

1. **Data-driven cards (definitions, not subclasses)** is the right call. Backed by ADR-0005 (Objects over IDs) and the Scaffold bridge, this scales without subclass explosion.

2. **CardRef rotation as a privacy mechanism** is genuinely clever. Server filters by visibility; observers see refs change but cannot correlate old↔new. Same mechanism handles initial reveal, hide-then-reveal, and shuffle-while-hidden uniformly. You'll read about a lot of TCG networking codebases that get this wrong; you didn't.

3. **Modifier ordering + source attribution + ID factory** is a coherent triple. Source-bulk-removal on attachment death is a one-liner. Determinism is preserved. This is doing a lot of load-bearing work cleanly.

4. **Sealed mutation surface (six payloads).** No "general escape hatch" for entity variables. Easy to audit.

### What is fragile

1. **VariableValue is a reference type hierarchy.** IntVariableValue : VariableValue, IVariableValue<int> is a class. Every time a modifier Apply(int current) returns its result wrapped (e.g., new IntVariableValue(current + amount)), or a BaseValues write stores new IntVariableValue(50), that's a heap allocation. Reads via GetVariable<int> unwrap to the inner type, so the call site is allocation-free for the cache hit, but every cache rebuild walks the modifier stack and folds — and the fold's intermediate values are wrapper instances. For high-modifier-count cards, this is the dominant alloc source on the entity hot path.

2. **String-keyed variables.** Variable.Key is a string. EntityVariableState.BaseValues and ModifierStacks are dictionaries keyed by Variable. Every read does a hash + equality check on (string, string). Convention says authors use static readonly Variable Vars.Attack = new("attack", "int") (so the instance is shared and reference-equality is enough), but nothing in the type system enforces that. An author who writes entity.GetVariable<int>(new Variable("attack","int")) at a call site allocates a new Variable every time and burns string hash work.

3. **Two-ID model leaks across many surfaces.** The rule "InstanceId for server-internal, CardRef for client-visible" is documented in card-model §"Useful Invariants," but every system that bridges them has to know:
   - EntityVariableState keyed by InstanceId.
   - CardMapState keyed by CardRef (and parallel by Card).
   - ZoneContentsState keyed by CardRef.
   - OwnershipState keyed by InstanceId.
   - CardVisibilityState keyed by InstanceId.
   - History entries: ZoneContentInserted carries CardRef; CardRefRotated carries both. 
   - Triggers, ongoing effects, attachments use Card object or InstanceId.
   
   This is a lot of "which ID am I supposed to use here?" surface for a game author and presentation programmer to hold in their head. The split is principled but the cognitive cost is real.

4. **Two parallel dictionaries in CardMapState (Cards and RefByCard)** means every CardRef rotation rewrites both. For a 100-card game, the ImmutableDictionary structural sharing keeps this O(log n), but the wins are linear in the number of slices touched per move (CardMapState + every ZoneContentsState containing the old ref + CardVisibilityState, all rebuilt as immutable records).

5. **WithCardMoved semantics aren't pinned.** MoveCardMutation says "removes from source ZoneContentsState, rotates in CardMapState, inserts into destination." That's three slices touching one operation, atomically batched. Good. But the rotation itself — what writes the old→new ref into history? Currently a prose description ("composite expansion in prose, not normative API"). When HistoryEnvelope is finally typed, this will be load-bearing.

6. **Modifier Apply signature returns a new value of the inner type.** VariableModifier<T>.Apply(T current) — fine for int (no alloc). But for any modifier with payload state (e.g., a future "set to specific value, but only above a threshold"), the modifier itself is heap allocated, lives in the stack, and serializes via EntityModifierEntry. The stack is IReadOnlyList<ActiveModifier> per variable. Folds walk that list each rebuild. This is fine for 1–3 modifiers per variable; it gets meaningful at 10+.

7. **No card prefab / authoring story.** CardDefinition is EntityDefinition (Scaffold), which is a ScriptableObject with an internal VariableBag. Game-specific definitions extend it (VillagerDefinition : EntityDefinition { public VillagerJob Job }). But:
   - How does the framework load the catalog?
   - How does a designer add a new card?
   - How are effects (the "recipe" per effects/04 §3) actually authored? Code? Data? Graph?
   - Serialization, asset migration, definition versioning are deferred (bl-authoring-feature).

   This isn't a card-variable concern per se but it's adjacent: variables are useless without a way to write the cards that have them.

## CONCERN 3: Performance and Memory

### The immutability tradeoff: where it earns its cost back

1. **Snapshot/rollback for AI search and replay.** A Store.Snapshot() is a reference to a record graph; restore is one swap. AI minimax over 1000 game states is feasible only because state is immutable. Hard to overstate how much this matters for a deckbuilder/TCG framework.

2. **Determinism.** Immutable + ordered dispatch + deterministic ID generation = byte-identical replays. Multiplayer reconciliation, tournament replay, regression testing — all ride on this.

3. **Coalesced notifications.** Atomic batches mean one notification per slice per batch, not one per mutation. Good.

4. **Structural sharing in ImmutableDictionary / ImmutableList.** A 60-card deck doesn't fully re-allocate when one card moves — only the touched tree paths. Still ~log₃₂(60) ≈ 2 internal node allocs per dictionary write; not zero, but not linear.

5. **Per-rebuild effective-value cache on StoreVariableStorage** keeps reads fast post-mutation (the fold doesn't run on every GetVariable, only on cache miss).

### Tracing MoveCardCommand allocation

This is the cleanest single command in the framework. Here's what allocates:

```
MoveCardCommand (record) → 1 alloc.
ctx.Store.Execute(new MoveCardPayload(...)) → 1 alloc.

Mutator fanout — for MoveCardPayload minimum:
  PileMoveMutator returns new PilesState with ImmutableDictionary<PileId, Pile> rebuilt 
    at affected entries → ~3-6 tree-node allocs (structural sharing) 
    + 2 new Pile records 
    + 2 new ImmutableList<CardRef> (one per pile) 
    → ~5-10 allocs each.
  
  LastMoveMutator returns new LastMoveState → 1 alloc.

Card-side composite expansion:
  CardMapState: 2 ImmutableDictionary rebuilds (Cards + RefByCard) 
    → ~6-10 tree-node allocs.
  ZoneContentsState source: new record + new ImmutableList<CardRef> 
    → ~3-6 allocs.
  ZoneContentsState destination: same → ~3-6 allocs.
  CardRef rotation: Guid.NewGuid() is struct (no alloc) but boxing/dictionary entries allocate.

Atomic commit, subscriber notifications fire — coalesced → handler closures may capture 
  context → per-subscription allocs.

HistoryEnvelope appended → new envelope record + new ImmutableList<HistoryEnvelope> 
  rebuilt at the tail → ~3-5 allocs. (Currently pseudocode but planned.)

After-fold runs (per-instance triggers) — each TriggerMatch is a record, each fold result 
  is a record/enum value, the fold list is rebuilt per phase.

Evaluate reads slices via State.Get<TState>() — Get itself allocates lookups but most 
  are cache hits.

If queue empties → OnQueueDrained → typically Actions.Set(new AvailableActionsSnapshot(templates)) 
  → new snapshot record + new template list + N ActionTemplate subtypes. 
  Snapshot construction is an allocation hot spot.
```

**Estimate: 30–60 allocations per single move command before any game-specific effects run.**

### Slay-the-Spire-style turn allocation

A typical turn (player plays 4 cards, each with a modest effect chain, ending with a draw of 5):

```
4 plays × ~50 allocs (move + execute + fold + evaluator + drain snapshot) = 200
~5–10 modifier mutations from card effects = 50–100
Trigger fold work = 50–100
Final draw = ~25–50
Total: 350–500 allocations per turn — most short-lived (Gen 0 collectible).
```

### Where the cost looks problematic

1. **Stacklands-style real-time tick is in the vision but architecturally incompatible.**
   - [VISION.md](http://VISION.md) lists "spatial card simulations" and [ARCHITECTURE.md](http://ARCHITECTURE.md) calls out "Real-time/tick scheduler" as a supported scheduler style. But:
   - 100 cards on a board, each with timer + recipe state, ticking at 60 FPS = 6000 mutations/sec.
   - At 30–60 allocs per mutation = 180k–360k allocs/sec.
   - Even with Gen-0 collection, this is a Mono GC stutter waiting to happen on Unity's mobile target.
   - The "richer schedulers as extensions" line in [RECOMMENDATIONS.md](http://RECOMMENDATIONS.md) is an unproven assertion. Real-time tick may need a fundamentally different state tier (mutable hot state, periodic snapshot-on-action), not just a different scheduler.

2. **VariableValue is a class hierarchy, not a struct/tagged union.** This is the single biggest GC lever. A discriminated union (struct VariableValue { Tag Tag; int IntValue; float FloatValue; bool BoolValue; ... }) with 16–24 bytes inline would eliminate per-modifier-fold allocations entirely. Trade-off is loss of polymorphic dispatch on Apply — but that can be moved to the modifier (which is heap-allocated anyway since it's serialized into the modifier stack).

3. **Two parallel ImmutableDictionarys in CardMapState** double the alloc cost of every CardRef rotation. A single combined structure (ImmutableDictionary<CardRef, Card> plus a Card→CardRef lookup as an index built lazily, or a custom bidirectional map) halves it. The reverse-lookup justification ("RefOf(card) is called inside every mutation") is correct but doesn't require a parallel slice.

4. **No object pooling** for GameCommand, GameAction, CommandResult, StateMutation payloads. These are short-lived records. They're allocated, dispatched, awaited, and dropped. Pool by command type would cut a significant chunk of Gen 0 work — but pooling records that are used in async chains (effects awaiting scope.Dispatch results) needs careful lifecycle. No discussion of this anywhere in the docs.

5. **HistoryState.Envelopes as ImmutableList<HistoryEnvelope>.** Every command appends one envelope. Over a 30-turn game with 200 commands, that's 200 immutable-list rebuilds with the envelope list growing linearly. ImmutableList's tree-rebuild cost is O(log n) per append — totally fine for 200 envelopes, problematic at 10k+. For replay seeking, ImmutableList is OK; for high-volume history (tick-based games), it's another ImmutableList trap.

6. **Snapshot construction allocates the full template set** on every drain. AvailableActionsSnapshot.Templates is IReadOnlyList<ActionTemplate> — typically a fresh List<> every OnQueueDrained call. For a TCG with hundreds of legal targets per turn, this is a meaningful per-drain allocation. Not catastrophic, but worth thinking about: do we need to publish a new snapshot when nothing changed, or can the rule diff?

7. **No published perf budget anywhere in the docs.** No "single command should resolve in <1ms with 100 cards in zones." No "GC budget per command." No stress test target. This is the most concerning architectural gap — you're committed to an immutable design with non-trivial allocation cost and no measure of when "the immutable tax" stops being acceptable. Without budgets, every future "should we change X to be faster?" debate becomes opinion.

### Options if you want to move

1. **Discriminated-union VariableValue as a struct.** Biggest single GC win available; cheap-ish change because the payload type id is already there. Trade-off: harder to add new value types late (struct must be future-proofed).

2. **Pool GameCommand / GameAction / payloads.** Per-type pools, returned at envelope-close. Fits the synchronous handler model; complicates async effect chains because the result is held across awaits — but most results are short-lived enough that returning at effect-end is fine.

3. **Two-tier state.** Canonical immutable slices (snapshot/rollback) + transient mutable hot state (timers, animation queue, presentation cache). The current design forces everything through the Store; this would explicitly carve out "things that don't need rollback" and put them outside it. This is the architectural choice that enables real-time tick games without fighting the framework.

4. **Establish perf budgets and stress benchmarks now**, before the implementation pass. A 50ms-per-command headline budget feels luxurious for TCG; <2ms feels right; <0.5ms enables AI search at acceptable rates.

5. **Alternative immutable libraries.** ImmutableDictionary from System.Collections.Immutable is conservative; libraries like ImTools or LanguageExt have lower-allocation persistent maps. Worth a spike.

## BROADER ARCHITECTURE FINDINGS

### Solid foundations to keep

1. **Three-layer mutation discipline** (Effects orchestrate, Handlers invoke mutators, Mutators produce state) — this is genuinely good. It's enforced by service surfaces (IEffectScope doesn't have a Store; IHandlerContext does). Easy to teach, hard to violate accidentally.

2. **Mutator + Payload registry** — one payload type, multiple mutators auto-fanned out by Scaffold, atomic commit. The Pile Counter sample (MoveCardPayload triggering both PileMoveMutator and LastMoveMutator) shows it scales. Don't change this.

3. **State-based evaluator pattern** (Evaluate reads state, doesn't switch on command type) is a strong invariant. Makes effect copies, token spawns, and cross-source reactions all work uniformly without special cases.

4. **Trigger fold** (OnBefore/OnAfter with discriminated Cancel/Replace/Modify outcomes) handles replacement-of-replacements cleanly. Cleaner than MTG's literal stack-of-replacements semantics.

5. **CardRef rotation for privacy** + server-side canonical state + transport-time filtering is a coherent multiplayer story. Almost ready for networking even though networking is deferred.

6. **ADR-0005** (Objects over IDs) with Identifier<T> at boundaries — this killed a real risk (ID-shaped APIs everywhere, unclear when to look something up). The boundary discipline is preserved cleanly.

### What looks overcomplicated

1. **The two-ID model is more complex than the value it adds.** InstanceId vs CardRef is principled, but the framework is committing to it before networking work has actually started. If 80% of users build single-player games, they pay the conceptual cost (every read/write thinks "which ID?") for 0% of the benefit. 

   **An option to consider:** Keep CardRef as a transport-time projection (computed at the network adapter, not stored in CardMapState) — and let the rules see only InstanceId. This collapses three slices (CardMapState, the visibility-rotation logic) into one, and removes "which ID?" from the rules-author's mental model entirely. You lose snapshot-of-CardRef-state (which matters for server-side replay correlation across visibility changes) but you regain a simpler model. Worth weighing.

2. **One slice per entity for variables.** Currently EntityVariableState is keyed by InstanceId — one slice per entity. The Store tracks these individually for snapshot, subscription, and lookup. An alternative is one big EntityVariablesState slice (ImmutableDictionary<InstanceId, EntityVariableData>) with the bridge subscribing to the dictionary. Trade-off: lose granular per-entity subscriptions (subscribe to "anything about entity X") but gain dramatic reduction in slice count and per-slice allocation overhead. Worth a spike to measure.

3. **OnQueueDrained doing snapshot-build + dispatch + side-effects-via-services** is a heavy method. It writes through Actions, optionally through Pending (re-entry), returns DrainResult.Dispatch. The contract guarantees got softened to allow this ("observer-shaped" relaxes for OnIncomingCommand and OnQueueDrained"). The drain hook is becoming the kitchen-sink for game-wide flow logic. As games grow, this method will too — and there's no composition contract yet (`oq-gamerules-composition` is open).

## CRITICAL MISSING ARTIFACTS

1. **No perf budget, no stress tests, no benchmarks** — for an immutable-everything Unity framework, this is the elephant in the room. Decisions like "ImmutableDictionary vs custom persistent map" can't be made without numbers.

2. **No authoring story for cards** (bl-authoring-feature). The framework describes how cards behave but not how they're defined by content authors. ScriptableObjects with Effect-recipe references? JSON-driven? Code-only? This decision will reshape CardDefinition, the variable-key registration story, and the Effect "recipe" format.

3. **No story for "effect recipes."** effects/04 §3 says "the card definition holds the recipe — how the effect is constructed for new instances. The recipe shape (data, code, graph, or hybrid) is out of scope." This is THE design question for any data-driven card game and it's deferred.

4. **HistoryEnvelope is still pseudocode.** Every framework slice that depends on it (HistoryState, replay, multiplayer, presentation history loop) is built on a TBD type. This blocks any serious networking or replay work.

5. **Real-time tick scheduler is in the vision but not designed.** Either remove from vision, or commit to a different state tier for tick-based games (see Concern 3 options).

6. **Decision routing via type-only Wait<TCommand>** is fragile for anything beyond one-target-at-a-time decisions. oq-fsm-game-state is the eventual successor but hasn't been spiked. A game with two simultaneous decisions (e.g., MTG split-second triggers, or Stacklands two players assigning workers concurrently) breaks this. Fine to defer; risky to forget.

## ARCHITECTURAL CHOICES WORTH QUESTIONING

1. **VariableValue as class hierarchy.** Already discussed. The single biggest performance lever the framework has not pulled.

2. **Two parallel maps in CardMapState** (Cards + RefByCard). Doubles every CardRef rotation cost. The reverse-lookup justification is real but doesn't require a parallel slice — could be a transient cache, or a single bidirectional map type.

3. **Allowing handlers to mutate state via raw ctx.Store.Execute(payload) AND through IMutableEntity simultaneously.** Two paths for the same operation. The "discipline" rules are documented in prose. A typed handler-side surface that only exposes the right path per case would be safer.

4. **Slice catalog grows organically.** Framework owns 3 slices (AvailableActionsState, EngineState, HistoryState); games define more (PilesState, LastMoveState, etc.); the bridge adds more (EntityVariableState per entity, CardMapState, OwnershipState, ZoneContentsState per zone, CardVisibilityState). There's no upper bound or governance on slice count. As features land (lifecycle, attachment storage, presentation cache), this just grows. A registered-slice budget or "single canonical store" review would help.

5. **No "cold storage" tier.** Definitions and authored data live in EntityDefinition (ScriptableObjects). Runtime instance state lives in slices. There's no concept of "frozen state during animation playback" or "snapshot-frozen during AI search" — every layer assumes it can mutate. For AI search this is fine (you snapshot, search, discard). For animation it might be wasteful.

## HEADLINE INSIGHTS

1. **You have a solid foundation in the Mutator/Payload + three-layer separation.** Don't break this looking for performance — the layering is what makes the framework safe at all.

2. **The biggest GC lever you haven't pulled is VariableValue being a class.** A struct/tagged-union representation eliminates the dominant alloc on entity hot paths. Probably worth a spike before the implementation pass starts.

3. **Real-time tick games are in the vision but the architecture cannot support them without a separate mutable state tier.** Either remove from vision now, or commit to a two-tier state model. This is the single biggest scope-vs-architecture tension.

4. **Critical missing artifact: a performance budget.** Every "should we make X immutable / pooled / cached?" debate needs a number. <2ms / <5KB allocations per single command at 100-card baseline is a starting bid.

5. **The two-ID card model (InstanceId + CardRef) is principled but expensive** in cognitive cost and slice churn. Worth re-examining whether **CardRef can be a transport-time projection rather than a stored slice key.** This would:
   - Eliminate the RefByCard dictionary (one allocation source gone)
   - Simplify snapshots (CardRef becomes a computed projection, not state)
   - Remove "which ID?" from the rules-author's mental model
   - Separate concerns: Card is entity, CardRef is visibility/transport layer
   
   Defers the decision until networking actually starts, but enables a simpler interim model for single-player games.

6. **Authoring is unbuilt and load-bearing.** Phase 0–2 are implementation-ready, but without a card authoring story, the implementation will discover constraints late. A Spike on "how does a designer write the Fireball card definition + effect recipe?" before Phase 2 ships will save a redesign later.

7. **OnQueueDrained is becoming the kitchen-sink method.** Snapshot publication, follow-up dispatch, drain re-entry. As games grow, this method does too. The composition contract (oq-gamerules-composition) needs to land before the first game forces a refactor.

## CONCLUSION

Card-Framework has **solid architectural foundations** (three-layer mutation, state-based evaluation, trigger subscriptions, snapshot/rollback). 

**Primary pain points are solvable** via targeted spikes:
- CardRef externalization (architectural improvement, potential allocation recovery)
- VariableValue struct prototype (allocation reduction)
- Perf budget + tests (visibility + prevention)
- Entity registry formalization (fragility reduction)

**Real-time tick is a design gap**, not a bug fix. Separate spike required.

**Next critical decisions:**
1. CardRef externalization — simplifies multiple concerns if feasible
2. VariableValue struct — single biggest performance lever
3. Authoring model — unblocks game authors and discovers constraints early
4. Perf budgets — enables objective trade-off decisions

The framework is research-solid and ready for Phase 2 implementation with the caveat that authoring patterns should be spiked early and performance budgets established before committing to immutable-everywhere for tick-based games.
