# Legends of Runeterra Architecture Analysis

> **Status: concluded.** External-architecture analysis spike. Findings inform framework refoundation decision.

This document analyses Riot Games' *Legends of Runeterra* (LoR) — a Unity-based digital CCG — as prior art for an event-sourced card-game framework. Unlike SabberStone / Brimstone / Fireplace, LoR has no open-source server, so this analysis combines Riot's official engineering posts, the Data Dragon static-data product, the local Game Client API, and observable behaviour of the in-game **Oracle's Eye** preview. Sources are labelled official, community-RE'd, or speculation throughout.

## 1. Core Architecture

LoR is a **server-authoritative** Unity title written almost entirely in C# on both client and server ([official, Riot Tech Blog](https://technology.riotgames.com/news/bringing-features-life-legends-runeterra)). The CI/CD post ([official](https://technology.riotgames.com/news/legends-runeterra-cicd-pipeline)) confirms the game server can be run headless in a Docker swarm and that **debug builds expose an HTTP endpoint for direct game control** ("play card", "attack", "concede") — meaning the server's authoritative API is a structured command surface, not a UI-coupled state machine. Functional tests are written in `pytest` and drive the server directly. The client is a "thin" renderer in the same sense as Hearthstone's: it submits intents and consumes a state stream.

There is no public source release. The IL2CPP-compiled Unity client is reverse-engineerable (Il2CppInspector explicitly lists LoR's striped-XOR obfuscation as supported, [community](https://github.com/djkaty/Il2CppInspector)), but no full architectural dump appears to be publicly archived.

## 2. State Model

LoR's static card data is shipped as **Data Dragon** JSON bundles split into a core bundle (factions, keywords, rules) and per-set bundles ([official](https://developer.riotgames.com/docs/lor)). Each card record carries fields like `cardCode`, `attack`, `health`, `cost`, `keywords` / `keywordRefs`, `spellSpeed` / `spellSpeedRef`, `rarity`, `type`, `subtypes`, `associatedCardRefs`, `description`, `levelupDescription`. The locale-stable `*Ref` fields suggest the runtime keys cards and keywords by symbolic enum, not localised strings — analogous to Hearthstone's `CardDefs.xml` + `GameTag` enum split.

The **runtime** entity model is not documented publicly, but the local Game Client API (`https://127.0.0.1:21337`, [official](https://developer.riotgames.com/docs/lor)) and the Overwolf game-events surface ([community wrapper](https://overwolf.github.io/api/games/events/legends-of-runeterra)) expose entities as `{ CardCode, CardID, LocalPlayer, TopLeftX/Y, Width, Height }` records — i.e., the client receives a flat list of *positioned, identified card instances* rather than a structural board tree. This is consistent with (but does **not** prove) a Hearthstone-style **entity-id + tag-bag** internal representation: positions and zones look like properties on a uniform entity record. Treat the tag-bag claim as *plausible inference*, not confirmed.

Hidden information is handled by per-side reveal flags: opponent hand cards are opaque until a Recall / Discard / Obliterate / explicit-create effect reveals them ([official support](https://support-legendsofruneterra.riotgames.com/hc/en-us/articles/360037188513-I-Can-See-My-Opponent-s-Card)). Once revealed, the flag is sticky for that instance — the same `ShowEntity` / `HideEntity` pattern Hearthstone uses.

## 3. History & Messaging

There is **no public equivalent of Hearthstone's `PowerHistory`** — no documented `BlockStart`/`BlockEnd` schema, no community-reverse-engineered packet capture has been published, and Riot has not shipped a downloadable replay file format. The closest community surfaces are:

- The local Game Client API, which is **polling-based** (deck list, card positions, last game result) rather than an event stream.
- Overwolf's game-events feed for LoR, also polled, surfacing `active_deck`, `local-card-data`, `card-positions`, and `match-info`.
- Third-party deck trackers (LoRSideTracker, Mobalytics, LoR Master) all build on these polled surfaces, not on a packet protocol.

Internally, the authoritative server almost certainly streams a structured update log to the client (no real-time CCG can ship without one), and the HTTP debug-control interface implies the server can be driven and inspected step-by-step. But the **wire-level event grammar is not public**, so any direct mapping to a `PowerHistoryBlock`-style envelope is *speculation*. The strongest signal that something block-like exists is Oracle's Eye (next section), which clearly requires the server to resolve a bounded sub-graph of effects and return a delta.

## 4. End-of-Round Preview ("Oracle's Eye")

This is the mechanic that motivated the doc. Oracle's Eye is a blue orb between the nexuses that, when hovered, shows the projected outcome of the **currently-declared but not-yet-resolved** state ([official](https://support-legendsofruneterra.riotgames.com/hc/en-us/articles/360036075473-Oracle-s-Eye), [wiki](https://leagueoflegends.fandom.com/wiki/Oracle's_Eye_(Legends_of_Runeterra))). It opens in three situations:

1. **Spell stack is non-empty** — Fast / Slow spells or Skills are on the stack waiting to resolve.
2. **Attackers have been declared** but combat hasn't resolved.
3. **Blockers have been declared** but combat hasn't resolved.

It does **not** open for Burst / Focus spells, unit plays, or landmarks because those resolve immediately on commit. It also does **not** preview Round End / Round Start triggers — those are independent of player action and not shown in the orb ([wiki](https://leagueoflegends.fandom.com/wiki/Keywords_(Legends_of_Runeterra)/Trigger)). The framework team's "end-of-turn preview" intuition is partially mistaken: LoR previews the **resolution of a committed stack / declared combat**, not the round-end trigger phase per se.

The decisive constraint for the framework's speculative-envelope question is this: **Oracle's Eye refuses to open when any outcome on the pending stack is not pre-determined.** Per a Rioter response on the dev tracker ([community capture](https://devtrackers.gg/legends-of-runeterra/p/448c42e7-oracle-s-eye-need-to-be-improved-in-regards-to-random-effects)), random effects make "all the other stuff random" once they cascade, so the team chose to disable the preview entirely rather than show a non-binding sample. The preview also won't open when the outcome depends on information hidden from the player (e.g., an opponent's face-down card in the resolution path).

What that implies for implementation: Oracle's Eye is best modelled as a **pure function** over the committed stack and the visible board — `resolve(stack, board) -> projected_board`, with the input being state that is *already locked in* by the players' previous commit actions. Because randomness and hidden info gate the preview off, the engine never has to commit to a speculative RNG draw it might roll back. This is consistent with two plausible implementations, both of which Riot would consider:

- **(A) Replayed simulation:** the server (or a deterministic client copy of the resolution engine) re-runs the same resolution logic in "dry" mode against a forked state, emits the deltas as if it were the real resolution, then discards them. Cheapest to build *if* the engine is already pure-ish — but the framework would need every effect handler to be referentially transparent.
- **(B) Eagerly-computed + held envelope:** the server resolves the stack the moment it becomes resolvable, holds the resulting delta envelope buffered, and only emits it (or discards + replaces it) when the players' next interaction either confirms ("pass") or invalidates ("add another spell") the committed prefix. This is the "speculative envelope" model and *would* require the framework's envelope abstraction to support a held-but-uncommitted state.

Public information does not distinguish (A) from (B). Both are compatible with the observed gating rules (no preview when RNG / hidden info is involved — because under (A) you'd get a binding-but-different roll on the real resolution, and under (B) you'd have to either commit the RNG early or recompute). The framework should plan as if (A) is the bar: a clean replay-style projection over committed state is sufficient to reproduce LoR's preview, and it does *not* require the envelope system to model speculative branches that may be rolled back. *Speculative envelope support is a nice-to-have, not a forcing function from this mechanic.*

## 5. Spell Stack & Priority

LoR's stack is a bounded LIFO of **at most 9 Fast/Slow entries plus 1 reserved Burst slot** ([wiki](https://leagueoflegends.fandom.com/wiki/Spell_(Legends_of_Runeterra))). Slow spells must be at the bottom; Burst resolves on commit and never sits on the stack; Fast can be played any time. Priority alternates between players after each push, and when both consecutive players pass, the stack resolves top-down. Round End is then driven by **initiative tracking**: the player who *last initiated an action* triggers first, then board-left-to-right within each side ([official support](https://support-legendsofruneterra.riotgames.com/hc/en-us/articles/360043734914-Order-Resolution-Mechanics-and-the-Tiebreaker-Rule)). This is closer to MTG's priority-passing stack than Hearthstone's "the active player's effects all resolve, then opponent's" chain — and it is what makes Oracle's Eye coherent: there's always a well-defined pending substructure to project.

## 6. Player Input

Player input is structured commands ("play card X targeting Y", "declare attackers [a, b, c]", "pass"). The debug HTTP server takes exactly these as REST calls ([Riot Tech Blog](https://technology.riotgames.com/news/legends-runeterra-cicd-pipeline)), strongly implying the production client wire-protocol uses the same shape. There is no public evidence of client-side prediction; the polled local API and game-server-authoritative posture suggest the same "dumb terminal" pattern as SabberStone's Kettle.

## 7. Client/Server & Networking

- **Transport:** undocumented binary protocol over the Riot game-traffic stack; not publicly RE'd to the level of detail Hearthstone's protocol has been.
- **Authority:** fully server-side; the client mutates only on receiving server deltas (inferred from the debug-HTTP architecture and the polled local API exposing only *observed* state, not predicted state).
- **Local introspection:** the `127.0.0.1:21337` Game Client API gives third-party trackers a polled, read-only view of deck + card-positions + match result; it is not a replay log ([official](https://developer.riotgames.com/docs/lor)).
- **Replays:** no first-party downloadable replay file format is documented; community trackers reconstruct game history by polling.

## Summary

LoR is a server-authoritative C#/Unity CCG whose static data is openly published (Data Dragon JSON) but whose runtime protocol and entity model are closed and only lightly reverse-engineered. The architecture is plausibly similar to Hearthstone's entity+tag + structured-delta-stream pattern, but this is **inference**, not confirmation.

The mechanic that drew the framework's attention — Oracle's Eye — is **not** a free-form speculative simulator. It only opens when the pending state is fully determined (no RNG, no hidden info), and it previews **the resolution of an already-committed stack or declared combat**, not the round-end trigger phase. This is implementable as a pure replay of the committed prefix against a forked state with no rollback semantics required of the envelope abstraction. The framework's envelope model therefore does **not** need to support speculative branching as a hard requirement to match LoR's behaviour; a replayable, deterministic resolution function over committed state is sufficient. Sources are mostly official-Riot or wiki — community RE coverage of LoR's wire protocol is thin compared to Hearthstone's, so anything described above as "runtime" carries a higher-than-usual speculation tax.
